Data Preparation

Overview

This section documents how the project’s two raw datasets are extracted, cleaned, and structured into analysis-ready tables.

Data Sources

The project combines two complementary datasets, both covering 2024: one describes the actual workforce and one describes employer demand.

Dataset Source What it is Scale
IPUMS USA U.S. Census American Community Survey (ACS) Public Use Microdata Sample, 2024 Individual-level survey microdata on people: demographics, employment, occupation, industry, and wages About 3.2M person records, narrowing to about 1.57M employed with valid wages
Lightcast Lightcast job-postings database, 2024 Online IT job postings: title, location, salary range, skills, education, and experience About 72K postings in the core table, expanding to millions of posting-skill records

The IPUMS data is the supply side, covering who is in the workforce and what they earn, and it underpins the clustering, gender classification, and wage-gap regression. The Lightcast data is the demand side, covering what employers advertise for, and it supplies the job-market context.

ETL Pipeline

The pipeline runs in three steps via etl/etl_pipeline.ipynb:

Step Notebook Module Output
Extract 01_extract.ipynb extract.py Raw DataFrame loaded into memory
Transform 02_transform.ipynb transform.py Cleaned, column-reduced DataFrame
Load 03_load.ipynb load.py Relational CSVs saved to data/processed/

Transform Decisions

  • Columns dropped: Metadata fields (URLs, timestamps), redundant code columns where NAME versions were kept, sparse skill/certification columns
  • Missing value strategies: Salary filled with median; education/employment type filled with Unknown; experience left as-is (null = not specified)
  • Red/Blue state join: POLITICAL_LEAN column ready to merge once state_political_lean.csv is supplied

Structuring & Cleaning the IPUMS Data

The IPUMS workforce data arrives as one wide, flat file in which every row is a single person and household attributes are repeated on each person record. Instead of analyzing that redundant table directly, it is normalized into a small relational schema that mirrors the natural household-to-person hierarchy, so each table has a clear purpose and the analysis joins only the columns it needs.

Relational schema

Table Key What it holds
household SERIAL One row per household: state, group-quarters type, household weight
person SERIAL, PERNUM Demographics: sex, age, race, person weight
employment SERIAL, PERNUM Labor-market facts: employment status, occupation, industry, wage
employed_only SERIAL, PERNUM Analysis-ready slice: employed people with a valid wage

Cleaning during restructuring

Two cleaning decisions are applied before any table is written. The wage field uses the IPUMS sentinel value 999999 to mean “not applicable,” so those entries are recoded to missing rather than treated as real income. The sample is then restricted to people living in households (group-quarters codes 1 and 2), which removes institutional populations such as dormitories and prisons whose labor-market behavior is not comparable to the general workforce. Numeric codes for sex, race, state, and employment status are mapped to readable labels so every downstream chart and table is self-explaining.

The analysis table: employed_only

From these tables a single analysis-ready slice, employed_only, is built for the workforce analysis. It keeps only currently employed people who have a valid wage, and carries exactly the columns the models need: sex, age, race, state, occupation, industry, wage, and person weight. This is the table the clustering, the gender classifier, and the wage-gap regression all read from. Distinct occupation and industry codes are also saved as small lookup tables for reference.

A second cleaning pass at load time

A lighter, final cleaning pass lives in the shared loader module (analysis/utils.py) and runs every time the data is loaded, so the modeling never re-implements cleaning. The employment loader keeps only positive wages, drops records missing sex or state, maps the detailed industry codes into broad sectors, and discards anything outside those sectors. A shared base loader removes duplicate records by ID, and the location loader parses a clean two-letter state code from the metropolitan-area name field (MSA_NAME_INCOMING). Centralizing the final cleaning here means every exploratory chart and every model sees the same cleaned population.

Connecting the Two Datasets

Because IPUMS describes individual workers and Lightcast describes job postings, the two share no common records. There is no person-to-posting key linking them, so they are joined only at the level where they genuinely overlap, which is geography. Each dataset is aggregated to the state level (workforce summaries from IPUMS, posting volume and demand from Lightcast) and merged on state, so the cross-dataset analysis is presented per state rather than per individual. Both datasets cover 2024, so they describe the same period.

A finer join on occupation or industry is not possible as the data stands, because the two use different classification systems. IPUMS codes occupation and industry with the Census OCC and IND schemes, while Lightcast uses the federal SOC and NAICS schemes. Translating between them would require an external crosswalk that is not part of this data, and any such mapping would introduce its own approximation, whereas the state-level join is exact and needs no translation. This constraint is the reason the geographic comparisons stop at the state grain.
